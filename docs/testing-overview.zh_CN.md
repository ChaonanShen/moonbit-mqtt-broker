# 测试体系总览

本文只说明测试类别、执行阶段与责任分工。具体命令、断言和发布门槛以[发布前测试与验收操作手册](https://github.com/ChaonanShen/moonbit-mqtt-broker/blob/release/0.3.0/docs/release-verification.zh_CN.md)为准。项目的开发和用户手动测试都在远端唯一工作区 `/home/scn/moonbit-mqtt-broker` 进行；这里的“自行运行”不指在 Windows 建立源码副本。

| 测试类别 | 开发过程中 | 功能开发结束后 | 主要执行位置 |
| --- | --- | --- | --- |
| 格式、类型、编译与链接 | 按当前改动选必要检查 | 在候选提交上完整检查 | 开发侧定向；CI 完整执行 |
| 单元与协议边界 | 对新接口、高风险不变量和失败复现做少量定向测试 | 运行适用的完整测试集合 | 开发侧定向；CI 完整执行 |
| 网络互操作、认证安全、资源、持久化与运维 | 只验证正在处理的风险或最小场景 | 运行相关功能矩阵及兼容场景 | 主要由 CI 执行 |
| 发布包与运行环境 | 仅在新增依赖等风险出现时做必要原型 | 从已提交源码重建发布包，并在隔离运行环境检查 | CI 的严格分发验证 |
| 压力、稳定性与性能 | 必要时先做短夹具检查，不预跑完整长测 | 固定候选再做适用的完整测量 | 优先 CI；无适用 runner 时交用户 |
| 真实浏览器、指定硬件或其他难以自动化的环境 | 不作为日常开发全套运行 | 有明确覆盖缺口时单列验收 | 用户在远端按交接脚本自行运行 |

## 各阶段怎样安排

1. **开发中：**只做支持当前实现决策的编译检查、少量定向测试和必要的短场景。普通文档或机械修改通常不需要行为测试。
2. **实现收敛后：**备齐代码、测试、脚本和文档，在任务分支提交并推送。开发侧不先重复跑整套，CI 对该候选集中执行完整功能与严格分发验证。
3. **正式候选：**普通 push/PR CI 默认不启用扩展 soak；需要时在 CI 手动运行并设 `soak=true`。独立性能测试只有实际接入适用 CI job 时才算 CI 覆盖。
4. **用户自行运行：**仅针对 CI 没有合适环境或尚未接入的必测，以及用户希望独立复核的项目。agent 提供固定 SHA 的启动、实时日志和结果查询命令；用户启动后，agent 再核对证据。

开发检查通过、实现交付、CI 通过和正式验收是不同状态。正式验收要求同一候选 SHA 的适用测试完整结束，并核对最终退出码、运行环境记录与产物哈希；失败、超时或缺少结束记录均不能算通过。

P1-01 的默认 push CI 包含 WAL 功能与四环境 strict 持久卷门禁；扩展 strict soak 由 `soak=true` 启动，固定磁盘三模式性能仍由用户按固定 SHA 在远端执行。
